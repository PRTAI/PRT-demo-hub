# 需求中心与 Demo 绑定

## 使用流程

1. 产品经理或商务进入侧栏“需求中心”，填写标题、需求内容及可选业务分类，可选择多位指定查看人员、上传一个或多个需求文档，再点击“发布需求”。人员和文档均非必填，正文建议说明业务背景、演示场景、所需数据及验收标准，附件不会自动解析为正文。需求状态支持“进行中”“待更新”“已交付”“已关闭”，只有产品经理或商务可以修改状态。
2. 被指定的员工或主管可查看需求及下载文档，在需求详情点击“上传 Demo”即可打开数据工作台上传界面，当前需求会默认选中；也可以从“我的 Demo”上传后手动选择需求。侧栏“我的需求”集中显示指定给当前账号的需求。员工只读；主管还可把自己可见的需求转发给多位员工。
3. 草稿允许暂不绑定。提交主管审核、直接发布或恢复发布时，后端检查 Demo 至少关联一个需求，没有绑定则拒绝操作并提示补充。
4. 需求详情展示当前用户有权查看的关联 Demo，可以跳转 Demo 详情；Demo 详情展示关联需求，可以反向跳转。
5. 原需求发布人可在需求详情中“绑定已有 Demo”，只允许选择自己有权查看的 Demo。Demo 编辑者在 Demo 编辑页选择关联需求。

## 权限与关系

| 操作 | 权限 |
| --- | --- |
| 查看、搜索需求及下载附件 | 产品经理和商务查看全部；其余已启用且已分配角色的用户仅查看指定给自己的需求。 |
| 发布需求 | 产品经理或商务；单独的员工、主管、管理员角色不能发布。 |
| 编辑需求正文、分类 | 仍具有产品经理或商务角色的原发布人。 |
| 修改需求状态 | 产品经理或商务，可修改全部可见需求；原关闭、重开接口继续仅限原发布人使用。 |
| 上传需求文档、替换或移除指定人员 | 仍具有产品经理或商务角色的原发布人；文档单文件大小沿用平台配置限制。 |
| 转发需求并追加关联人员 | 产品经理、商务可转发给已启用的主管或员工；主管仅可转发自己可见的需求给已启用的员工。 |
| 在需求中心绑定、解绑已有 Demo | 当前需求的原发布人；每次同时检查 Demo 可见性。Demo 编辑者在 Demo 编辑页调整关联。 |
| 查看关联 Demo、文件及说明 | 沿用现有 Demo 权限，绑定不会自动授权，也不会改变商务的说明字段限制。 |

绑定为多对多关系：一个需求可以关联多个 Demo，一个 Demo 最多关联 20 个需求。关系存储在 Demo 层，所有版本共用；提交和发布快照保存当时的需求信息，后续修改不覆盖历史快照。

指定人员为可选项；未指定任何人员时，只有产品经理和商务能在需求中心看到该需求。文档下载接口会独立校验当前查看权限，取消指定后立即拒绝下载。非商务、非产品经理即使拥有 Demo 编辑权限，也无法在需求中心修改正文、状态或 Demo 绑定；主管可以通过转发追加员工。“项目经理”按平台现有“产品经理（pm）”角色处理。

关闭需求会阻止新的绑定，已经绑定的 Demo 保留关系并允许继续完善。待更新需求仍允许补充 Demo；重新开启后恢复为进行中。Demo 被主管退回时，关联的进行中需求自动变为“待更新”；已交付或已关闭需求不被自动改变。待审核或含已发布版本的 Demo 不能解除最后一个需求；可先绑定另一个需求再解除旧关系，避免审核中或已发布的 Demo 失去业务依据。

需求修改和绑定修改均检查版本号，发生冲突时拒绝覆盖；绑定操作和审计记录在同一数据库事务中提交。编辑 Demo 保存说明及需求绑定也在同一事务中完成。

## 多人转发

在“需求中心”或“我的需求”打开需求详情，点击“转发需求”，搜索并勾选多位人员，再点击“确认转发”。已关联人员显示为勾选且不可重复选择；成功后自动刷新关联人员，接收人立即可以在“我的需求”中查看需求、下载附件。

产品经理和商务可以转发全部可见需求，不要求自己是原发布人，接收人须具有主管或员工角色。仅有主管权限的账号只能转发指定给自己的需求，接收人须具有员工角色且不能兼任主管；当前可选择全部已启用员工，不限制为该主管的下属。兼任产品经理或商务的主管按合并权限可以转发给主管和员工。单独的员工、管理员没有转发权限。

每条需求最多关联 100 人。转发只追加关联，不移除已有人员，不改变发布人、需求正文、状态、附件或 Demo 权限。重复人员自动去重；停用、已删除、没有接收角色的账号以及自己不可作为接收人。转发操作记录到管理审计，保留新增人员及操作人。页面打开后人员角色、启用状态或需求权限发生变化时，提交会再次校验；并发修改或转发会提示刷新，不能覆盖已有新关联。可点击“刷新人员”后重新选择并提交。

复用现有人员关联表，无需手动迁移数据或增加 `.env` 配置。更新部署时继续使用原数据卷，按 [Windows Docker 更新步骤](windows-docker-guide.md#更新当前已运行的容器并保留旧数据)备份、构建镜像并重建容器。

## 发布通知

Demo 审核通过发布、主管直接发布或恢复发布时，自动通过飞书机器人通知平台内全部已启用的产品经理，以及该 Demo 关联需求的商务发布人。多条需求对应多位商务时全部通知；同一商务发布多条需求，或同时拥有产品经理角色、被额外抄送，均只接收一条该次发布通知。产品经理和对应商务即使是本次操作人，也会收到自动通知。

“对应商务”目前按关联需求的发布人确定，且发送时仍须具有商务角色。产品经理发布的需求不会额外通知未关联的商务；如需通知其他人员，可在发布确认框中额外抄送。沿用原有归属员工通知规则，归属员工是操作人时不重复通知，兼任产品经理或对应商务时仍收到自动通知。

消息包含 Demo 名称、版本、归属员工、发布时的关联需求标题和飞书应用详情入口，不发送原始文件或成本等说明字段。关闭的需求保留原有绑定，对应商务仍属于发布通知范围；仅保存草稿、提交审核、添加绑定或修改需求不触发发布通知。

通知与发布状态在同一数据库事务中入队，发送失败不会回滚发布；复用现有失败重试、飞书 UUID 去重和管理员手动重试机制。发送前再次检查版本状态、账号是否启用、产品经理角色或商务与当前关联需求的关系，过时任务会跳过。飞书应用需已启用机器人、配置应用凭据及发送消息权限，并将接收人包含在应用可用范围内。管理员可在“平台设置 → 飞书通知”查看送达或失败记录；体验环境只验证入队，不实际发送消息，历史发布不补发。

## 更新与数据兼容

构建前端并重启后端即可加载功能，无需手动执行 SQL。启动时自动创建 `requirements`、`asset_requirements`、`requirement_assignees`、`requirement_files` 表及索引；现有 Demo、文件和版本保持原样，不自动为真实数据生成需求，也不自动指定历史需求的人员。原发布人需要编辑历史需求补选人员。需求文档复用现有文件存储，数据库关系与文档一起纳入备份恢复。

当前 Windows Docker 部署按 [保留原数据卷更新步骤](windows-docker-guide.md#更新当前已运行的容器并保留旧数据)执行，使用 `compose.production.yaml` 和 `compose.keep-data.yaml` 重建镜像与容器。无需在宿主机执行下面的原生 Node.js 命令。

历史已发布 Demo 可以继续访问，后续提交、发布或恢复发布前需补绑需求。历史待审核 Demo 在审核通过前也需补绑，可由需求发布人在需求中心操作。新建版本沿用 Demo 的绑定关系。现有备份与恢复会包含需求和绑定关系。

```powershell
npm run build
.\scripts\stop-host.ps1
.\scripts\start-host.ps1
```

体验环境首次初始化时包含一条明确标记为合成样例的需求及其 Demo 绑定；已有体验目录也按历史数据处理，可直接在需求中心补充需求。正式环境不加入样例需求。

## 验证

自动化测试覆盖发布与管理权限、多对多绑定、Demo 访问隔离、商务绑定与内容权限隔离、提交发布校验、最后一个绑定保护、关闭与重开需求、并发冲突、事务回滚、备份恢复，以及发布通知接收人、去重、消息需求快照、飞书失败重试和发送前关系复核。

```powershell
npm test
npm run build
```
